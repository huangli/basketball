# 篮球进球检测：人工判读成本压缩——需求文档

> 版本：2026-07-28。本文档自包含，面向不了解本项目的读者，
> 目的是请对方在读懂现状后，给出「在召回不降的前提下压缩人工判读成本」的技术方案。
> 文中所有数字均来自实测记录或数据文件，未验证的项标注「待确认」。

---

## 1. 项目背景与最终目标

业余篮球队「半截篮」的比赛/训练录像需要剪辑出**进球集锦**：

- 检测每一场录像中的全部进球（球入网瞬间，称「锚点」）；
- 按规格切片（锚点前 4 秒 + 后 2 秒）合成两类成品，按场次分目录存放：
  - 队伍进球集锦：`output/<场次>/队伍_XX_进球集锦.mp4`
  - 个人进球合集：`output/<场次>/个人_XX_进球合集.mp4`（进球归属目前由人工标注）
- 成品规格：1080p、50fps、H.264 + AAC；输出比例跟随素材等比缩放不裁切
  （当前 16:9 素材出 1920×1080）。

素材持续流入：每打一场就新增一批视频。**一个场次的典型规模是 300 个文件 / 约 71 分钟**
（当前唯一真实场次 20260722 即为此规模）。处理必须可断点续做、可重复执行。

**本文档要求解的问题**：当前流水线已能端到端跑通，但每批素材产生约 113 个候选事件
需要人工逐一判读；全量推进后此成本不可接受。详见 §7。

## 2. 素材事实（已 ffprobe 验证）

| 项 | 值 |
|---|---|
| 来源设备 | DJI（dji_mimo 命名），手持跟拍 |
| 编码 | HEVC，3840×2160（16:9），10-bit（yuv420p10le），59.94fps（60000/1001） |
| 文件粒度 | 小分段文件，平均约 14 秒/个；文件名即拍摄时间（`dji_mimo_YYYYMMDD_HHMMSS_...`） |
| 流结构 | 视频流 + 音频流 + data 流 + 缩略图流；转码需 `-map 0:v:0 -map 0:a:0` 显式选流 |
| 场次规模 | 300 文件 / 约 71 分钟（20260722 场次实测） |

内容特点（直接影响检测难度）：

- **手持跟拍，相机持续运动，篮筐在画面中位置不固定**；一场球使用**两个筐**（全场两端）；
- **训练与比赛混杂**：训练中的进球不进集锦（需识别但标记为不收）；
- 球在 1920 宽抽帧帧上仅 ~15–40px，入网瞬间常被筐/网/球员遮挡；
- 另有旧测试素材（20250419，114 文件，4:3 3840×2880，8-bit 50/100fps）已归档，
  仅作回归用，不是当前生产对象。

## 3. 硬件与环境约束

- **无独立 GPU**：AMD Ryzen AI 9 HX 370 + Radeon 890M 核显，32GB 内存；
  PyTorch 为 CPU 版（torch 2.13.0）。
- YOLO 推理实测：双模型（球 + 人）在 1920 宽抽帧帧上约 **1.1 秒/帧**（imgsz 1280）；
  按 5fps 抽帧折合约 **5.5 秒 CPU / 1 秒素材**。
- Python 3.14.3；ultralytics 8.4.104、opencv 5.0.0、numpy 2.4.3、pillow 12.3、
  open_clip_torch 3.3.0、scikit-learn 1.9.0、transformers、timm 1.0.28 已装。
- ffmpeg / ffprobe 8.1.2 在 PATH。
- **VLM 调用通道**：Kimi K3 模型，经 Kimi Code 订阅（`api.kimi.com/coding/v1`，支持图片输入）；
  **token 预算有限**（走订阅额度，非按量付费）；凭证 token 有效期仅 900 秒，
  脚本需每次调用前重读，**401 鉴权波浪是常态**，调用端必须有重试与缓存幂等。
- 出网代理 `127.0.0.1:7897`；HuggingFace 下载需 `HTTPS_PROXY=http://127.0.0.1:7897`。

## 4. 现有流水线（逐阶段 + 真实数字）

以下流水线已在一个 50 视频批次（20260722 场次首批，合计约 12 分钟素材）上端到端闭环，
数字均为该批次实测（2026-07-28 完成）。

```
原片
 ① 抽帧        5fps，缩放到 1920×1080（本地 ffmpeg）
 ② 双 YOLO     abdullahtarek_ball.pt（球）+ yolov8n.pt（人，持球排除用），CPU
 ③ MOT 候选    最近邻连轨迹，两条进球签名：
                a) 静止段：连续 ≥4 帧位移 <40px（球停在网里）
                b) 断轨重连：球消失 0.6–1.4s 后在 ≤400px 内重现且 0.8s 内有后继
                   （入网遮挡签名；a 类要求有前驱、b 类端点 conf≥0.3、盲区内无检测）
                过滤：死球（停 >3s）、持球（球框覆盖率 >0.5 落入人框）
 ④ VLM 精筛    Kimi K3 判「球进没进」，三值输出 YES / NO / UNCLEAR；
                本批次实际执行：单尺度 420 边长 + 「诚实模式」提示词
                （历史设计为 420/630 双尺度各判 1 次、任一 YES 保留，见 §5.1）
 ⑤ 事件合并    相邻候选（时间间隔 ≤2.0s）合并为事件；
                每事件出审核片段：按筐轨迹包围盒自适应裁剪（全程见筐），
                另出一段投球人广角视角；带事件编号水印
 ⑥ 人工标注    自包含标注网页 label.html，按键 J=进球 / P=进球不收 / F=不是，
                进度存 localStorage 可中断续标，一键导出 goals.json
 ⑦ 合成        build_highlight.py 按 goals.json 切片（前 4s + 后 2s），
                1920×1080 50fps，CRF 20 / preset medium，等比缩放+黑边补齐，
                同参数 concat 直接重封装
```

## 5. 已验证结论与已证伪清单

### 5.1 已验证成立

1. **断轨重连是召回关键**：入网遮挡 + 相机平移造成 0.8–1.6s 检测盲区，换模型/调参
   都突破不了 50% 召回；把「消失→重现」作为判据后，漏检全部找回（试点 4/4）。
2. **残余假阳性只能靠语义区分**：海报印刷球、球员腰带/膝盖、活球动作等假阳性
   conf 可达 0.8+，运动学规则无法区分，必须人或 VLM 判断。
3. **VLM 图片规格**：必须 840px 边长原图裁剪（448px 时球仅 ~8px 会漏看）、
   紧凑 3 帧（t0±1s）；K3 单次判定会摇摆，双尺度任一 YES 是为召回兜底。
4. **「候选位置到筐的距离」是目前唯一有区分度的零成本特征**（2026-07-28 调研，
   筐轨迹已逐事件提取）：
   - 3 个视频确认的真进球筐距分别为 66 / 260 / 570px（1920×1080 抽帧坐标系），
     全体候选中位数 540px；
   - 按筐距升序排审核顺序，能把 2/3 真进球推进前 13/113；但弹出滚远型进球（570px）
     会沉底——**只能调审核顺序，不能按筐距裁剪候选**。

### 5.2 已证伪（勿再尝试）

**模型类**：

- Lumos-88（basketball_yolo11.pt，224 张训练图、无人机视角）：假阳性爆炸 10–14 个/帧；
- 446f6e6e79_yolo11m：不可用（conf 0.01–0.4、框跨半屏）；
- zero-shot CLIP：正样本一半进不了 Top25；
- 4 球样本训练 sigLIP + logistic：留一文件交叉验证不泛化（估计需 20+ 进球样本）；
- K2.6 替代 K3 做精筛（2026-07-27 验证集实测）：进球级 2/4 vs K3 3/4，
  负样本留存 29/80 vs 8/80，召回精度双输，且 reasoning 输出 token 更高
  （~6.7K/候选 vs K3 ~4K/候选）。

**规则/特征类**：

- 筐 ROI 标定（v3 方案，曾花 ¥100+ 标注，三次翻车）；
- **筐位置/背景热点过滤**：筐+网在检测器眼里是常驻球形物，按位置过滤必然误杀进球；
- IoU>0.3 持球过滤：7886 条检测实证数学上不可触发（已修正为框覆盖率 >0.5）；
- LRF 低清检测（球 3–5px）、音频检测、像素/运动量法；
- VLM 448px 小图 / 5 帧稀释 / 严格 YES-NO 无分析提示词：都会全判 NO。

**轨迹物理特征替代 VLM（2026-07-28 调研证伪，326 候选 + 7 个视频确认真进球）**：

- 91% 候选是断轨重连型，其锚点恰落在 0.6–1.4s 检测盲区的**中点**——
  入网瞬间本来就没有轨迹数据，物理签名无从计算；
- 5fps 采样下入网过程只有 1–2 个采样点：「下落加速→骤停」签名在 7 个真进球上
  命中 0 个，「速度骤停」命中 1 个，而假候选上这两条规则的触发率为 3%–22%；
- 同批数据上 VLM 对 3 个确认真进球 3/3 全中。

### 5.3 VLM 的现实定位（2026-07-28 结论）

- 在「诚实模式」提示词下 K3 不再自动当裁判：365 候选中 325 个判 UNCLEAR、
  39 个 NO、仅 1 个 YES；
- 裸 YES（不给出理由的 YES）已按规则降级为 UNCLEAR；
- 实际价值 = **砍掉 11% 硬 NO（39/365）** + 提供筐居中裁剪与判定水印；
- 新提示词已收窄 UNCLEAR 定义（仅「看到投篮动作且球到筐区、结果瞬间没拍到」
  才算 UNCLEAR），**但尚未用于全量重判**。

### 5.4 已定入下一批的改进（不在本次求方案范围内，但方案需兼容）

- 事件排序按筐距（真球靠前，人工先标高密度区）；
- 事件聚类从纯时间 2.0s 改为时间 + 空间双条件
  （消同球重复事件：实测 39 对相邻事件中 14 对疑似同球）。

## 7. 需求与求方案的问题

### 7.1 核心问题

**在不降低进球级召回的前提下，压缩人工认真判读的事件数量。**

现状基线：每 50 个视频（约 12 分钟素材）产生 ~113 个事件需人工逐一判读；
按此外推全量 300 视频约 **680 个事件**。单事件 1–2 秒可判，但量级叠加后成为瓶颈。

理想目标：**认真判读 ≤30 个事件/场 + 对其余事件快速扫尾**；
或给出可信的自动判定（自动确认进球、自动剔除干扰，人只做抽查）。

### 7.2 硬约束

- **召回优先**：宁多报不漏报。任何会把真进球从人工视野中移除的步骤，
  必须证明进球级召回不降（在 §8 基准集上 20/20，并讨论置信度）；
- 训练球（rejected）可不收，但训练场景与比赛场景混杂，不能整段跳过；
- 算力：本机仅 CPU（§3）。**GPU 方案不被排除，但必须说明为什么 CPU 做不到、
  以及无 GPU 时的降级替代**；
- VLM 成本受订阅 token 预算约束（历史外推全量一场 ≈ 34M 输入 token，偏高）；
  外部按量 VLM（如 qwen-vl，估算 ~¥10/场）可作为对照但不预设采用；
- 方案必须能在 §6 的现有数据资产上**离线验证**，不要求先跑全量检测；
- 检测阶段（①–③）已稳定，方案重点在候选/事件的**精筛、排序与自动判定**；
  若要动 ①–③，需单独论证。

### 7.3 接受的路线（不限于）

其他 VLM / 视频理解模型、时序分类、轨迹 + 筐融合、主动学习、规则 + 模型混合等
任意路线；§5.2 列出的已证伪项请勿重复提出。

### 7.4 方案需给出的评估设计与指标

- **进球级召回**（在 §8 基准集与可构造的留出评估上）；
- **人工需认真判读的事件数**（压缩比）；
- **成本**：token 消耗、CPU 耗时、（如涉及）GPU 需求与外部 API 费用；
- 评估可复现：给出脚本/步骤，输入 §6 资产，输出上述指标；
- 指出方案在「弹出滚远型进球」「训练球混杂」「筐被遮挡」三类已知难点上的行为。

## 8. 验收基准

首批基准集（来自 §6 真值，覆盖 20260722 场次首批 50 个视频）：

- **正样本**：`work/20260722/goals.json` 中 20 条 `status=confirmed` 记录
  （锚点 = `anchor_time`，容差 ±2s 对齐到事件的 `anchor_t0`）；
- **负样本**：113 事件中被人工否决的 92 个（未出现在 goals.json 中的事件）；
- **特殊样本**：1 条 `rejected`（训练球，进球但不收）——方案需说明对它的处理；
- 复现方式：方案的筛选/排序逻辑作用于 `events_index.json` 的 113 个事件
  （及其关联的 candidates / mot_cache / hoops / vlm_cache_v2 数据），

## 附：术语

- **MOT**：多目标跟踪（Multi-Object Tracking）。这里指把逐帧球检测按最近邻连成轨迹。
- **断轨重连**：球在检测中消失 0.6–1.4 秒后在 ≤400px 内重现的轨迹模式；
  入网遮挡的典型签名，是 MOT 候选的两条规则之一。
- **静止段**：球连续 ≥4 帧位移 <40px；球停在网里的签名，另一条候选规则。
- **事件**：相邻候选（时间间隔 ≤2.0s）合并后的审核单元；一事件对应一段审核片段。
- **锚点**：进球时刻（球入网瞬间），单位秒；切片窗口 = 锚点前 4s + 后 2s。
- **候选**：MOT 阶段输出的单个疑似进球点（365 个）；合并后成为事件（113 个）。
- **裸 YES**：VLM 只回答 YES 但不给出任何理由的输出；按规则降级为 UNCLEAR。
- **三值判定**：VLM 输出 YES / NO / UNCLEAR 三档；UNCLEAR = 诚实模式下
  「看到投篮动作且球到筐区、但结果瞬间没拍到」（新提示词收窄后的定义）。
- **双尺度**：历史设计——同一候选以 420px 与 630px 两种边长裁剪送 VLM 各判一次，
  任一 YES 保留；首批 50 视频批次实际执行为单尺度 @420（诚实模式提示词）。
- **筐距**：候选位置（cx,cy）到该时刻筐轨迹位置的像素距离（1920×1080 抽帧坐标系）。
- **goals.json status 流转**：candidate（候选）→ confirmed（确认进球，进集锦）/
  rejected（进球但不收，如训练球）/ removed / uncertain；clipped / done 为合成后状态。
  仅 confirmed 进合成。
- **场次**：一次拍摄活动的全部素材，默认按文件名日期（YYYYMMDD）划分，如 20260722。
