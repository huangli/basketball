## 1. 阻断级（试点前必须改，否则会误杀自己的标杆）

### B1. §3.4 静止点判据「任意两点位移 < 30px」会判杀 0006 这个标杆案例

文档把 `0006@6s` 当作 `occlusion=true` 的成功标杆，但用 `work/investigate_0006/REPORT.md` 的坐标（均为 img 系 1920×1440）反验，判据不成立。

入网静止段真实坐标：

```
6.0s  (929, 798)   conf 0.05  ← 谷底/入网瞬间
6.2s  (952, 799)   conf 0.39
6.4s  (961, 798)   conf 0.41
6.8s  (956, 795)   conf 0.79
```

- 6.0s ↔ 6.4s：x 差 32px，dy≈0 → 距离 32px > 30px。
- 这四帧是连续 ≥4 帧的静止段，但「段内任意两点位移 < 30px」被 (929,798)↔(961,798) 这对打破。

**根因**：篮球入网后在网里晃动一个球径量级（REPORT 原话「球在网中晃动」），真球 size 才 27–50px（img 系），晃动 ±16–32px 是物理常态。「任意两点 < 30px」对一个球径的晃动太小。

**建议**：判据口径从「任意两点」改成下面任一种，并标明用 0006 标杆标定过：

- 相邻帧位移 < 30px；或
- 各点到段几何中心位移 < ~40px（img 系，≈一个球径）。

否则试点验收 §5.1 的「0006 必须检出」会在判据层直接失败——方案还没跑就先把自己唯一的遮挡型 ground truth 排除了。

### B2. §5 验收「召回率 100%」与 §3.5 接触表生成逻辑不闭环，且与方案自身承认的漏检矛盾

- §5.4 要求「召回率 100%，漏检任一即不通过」，并要求「接触表覆盖全段让立哥能发现漏检」。
- 但 §3.5 接触表是按候选生成的（anchor±3s），轨迹聚类没产生的候选根本不会出表。凡 YOLO/聚类漏掉的进球，接触表上立哥看不到——验收 4 的「发现漏检」机制不存在。
- 同时 §6 明确承认「入网遮挡」「球员完全遮挡」「远筐小球」都会漏。一边把 100% 召回当硬门槛，一边承认会漏，门槛注定不通过。

**建议**：

- 补一个全文件概览接触表（低分辨率，原片或 LRF 整段 tile）作为独立步骤，让立哥通览找漏检——这才是召回率的兜底测量手段。
- 召回口径改为：「未遮挡进球召回 100%；遮挡/小球类记录漏检率并在试点报告量化」，不要拿必然漏检的 case 否决整个方案。

## 2. 重要（影响正确性/可运行性，建议试点前定）

### I1. §3.3 关联阈值 120px 未用 0007 真实飞行速度验证，飞行段可能断轨

「相邻帧位移 < 120px（≈600px/s）」对下落/飞行段偏小。文档 §1.2 给的 0007 轨迹是「高处(184)→下降(429)→静止(462)」：

```
184 → 429 = 245px
```

若这是 1–2 帧间隔（0.2–0.4s），瞬时速度可达 1200+px/s，远超 120px/帧。关联会在飞行段断裂，导致「飞行段 + 入网静止段」被切成两条短轨，静止段可能 < 4 帧被丢，或 conf 谷底帧落在断点上。

§3.3 这个阈值目前没有用 0007 飞行段数据标定过。建议试点前置（§5 已有「对 0007/0008 跑精细抽帧」）顺手测真实飞行速度，据此定阈值，或改用速度预测关联（简单线性外推 + 余量）而非纯最近邻。

### I2. §3.2 双模型交叉验证的「调用 yolov8n.pt」表述会引发实现歧义

「对 max(w,h)>55 的检测调用 yolov8n.pt 交叉验证」读起来像逐候选单独跑一次 yolov8n——那成本爆炸（每帧 3–4 个候选 × 2.5s）。正确且唯一可接受的做法是：每帧（或每文件）全画面跑一次 yolov8n 取 person 框集合，再与球框做位置/IoU 匹配。建议把这句改写成明确的全画面一次性流程，否则按字面实现会拖垮 §3.1 的性能预算。

### I3. occlusion=false 分支是方案最大的 precision 威胁，验收应前置量化

occlusion=false（静止点但无 conf 谷底）的判别力很弱：任何停在画面里的球——训练球放在地上、被人抱着、滚到角落、死球——都会被判候选。0007/0008 恰好是「球停在网里且高 conf」，这和「球被人抱着静止」在轨迹特征上区分不开，只能靠接触表靠立哥肉眼分。文档 §6/§5.6 已诚实标注要分开统计 precision，这点很好；强调：在试点三文件里 occlusion=false 的样本太少（可能就 0007/0008 各一个），precision 估不准。建议试点扩到能覆盖「非进球静止球」反例的文件，或全量铺开后再下 precision 结论，不要据三个文件就推全量。

### I4. 空心入网（静止段 < 4 帧）是召回的最大未知数，兜底尚未实现

空心球穿网快，在网中停留常 < 0.8s = 4 帧 @5fps，§3.4 的「≥4 帧静止」会系统性漏。半截篮这种娱乐局空心球占比可能不低。§6 给了兜底（轨迹末端位移单调减小 + conf 谷底，无需长静止段）但只在风险表一句话、未设计实现。§5.7 要求「标注是否有空心球」是对的，但建议明确：若试点空心球占比 > ~20%，§3.4 兜底必须实现并测过，否则不推全量，而不是留到全量后才发现系统性漏。

（更深一层：5fps 对「快速穿网」可能根本采不到「球在网中」的帧——采样定理问题。可以考虑候选窗口内局部加密 fps，列为优化。）

## 3. 次要 / 同步项（不阻断，但 §8 说要同步 SPEC，顺手处理）

- **S1. SPEC schema 版本号陈旧**：SPEC §2 示例还写 `version: 2`，实际 `goals.json` 已是 v3，本设计升 v4。§8 同步 SPEC 时一并把示例改成 v4；另外 §3.8 的 JSON 示例只给了单条记录，缺顶层 `{"version":4,"goals":[...]}` 结构，补上。
- **S2. SPEC §2 目录约定要补**：`work\detect\`、`work\track\`、`work\candidates\`、`work\review\` 都不在 SPEC §2 目录树里；且 `work\frames\` 语义已从 v3 的「LRF 480×360」变成 v4 的「原片 1920×1440」，要在 SPEC 里讲清楚，避免和归档的 `archive/v3/work/frames/` 混淆。
- **S3. AGENTS.md「进球检测流程」整段要改**：AGENTS.md 现在写的是「LRF 2fps 抽帧→拼 5×4→人工→原片精抽」，这是 v3。§8 说「检测流程一行同步」，但实际是整段范式变更（放弃 LRF、全画面 YOLO），不是改一行。同步时按整段替换。
- **S4. conf 谷底判据的「段首尾均值」含谷底帧，略循环**：「段内最低 conf < 段首尾均值×0.5」，而 anchor=段首很可能就是谷底帧（0006 的 6.0s），把谷底算进分母会拉低门槛。数值上对 0006 仍成立（验过：段首尾均值 0.42×0.5=0.21，`0.05<0.21`），鲁棒性够，但建议把「段首」明确定义为谷底帧的前一帧，逻辑更干净。

## 4. 设计上做对、值得肯定的地方

- 放弃筐心标定 + crop、改全画面——REPORT 数据（偏 500px、crop 反而更差）完全支持，方向正确。
- conf=0.04 低阈值捕遮挡弱信号 + 谷底作判据不作过滤——范式正确，这是能救 0006 的关键。
- 坐标 ×2 换算、slowmo 按 50/100fps 判定——与 `file_inventory.json` 一致（0006/0007/0008 全是 50fps → slowmo=false，本期检测阶段不涉及慢放，合理）。
- 性能量级（40s 文件 ~8min、全量 ~15h CPU）——按 2.5s/帧算成立，前提是 I2 的交叉验证别逐候选跑。

---

## 5. 一句话结论

范式转变方向正确、证据扎实，可以推进；但 §3.4 静止点判据（B1）和 §5 召回验收闭环（B2）是两个会在试点阶段自己绊倒自己的硬伤，建议先修这两条再跑 0006/0007/0008。其余 I1–I4 建议在试点前置数据采集里顺手标定（飞行速度、occlusion=false precision、空心球占比），不要等全量铺开再发现。
